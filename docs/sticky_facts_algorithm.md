# Sticky Facts: как это реализовано в AgentsCore

Документ описывает **фактическую реализацию** стратегии управления контекстом
"Sticky Facts" (`agents_core/repository.py`), даёт пошаговую цепочку curl-примеров
и сравнивает поведение с исходным ТЗ. Все ссылки на код — актуальная версия
`agents_core/repository.py`.

## 1. Алгоритм пошагово

### 1.1. Что хранится

У каждого **пользовательского** сообщения (`Message.facts`, `agents_core/models.py:329`)
может быть сохранён JSON-снимок фактов на момент отправки этого сообщения:

```json
{
  "user_name": {"value": "Алиса", "confidence": 0.95},
  "goal": {"value": "мигрировать БД на PostgreSQL", "confidence": 0.8}
}
```

Формат — ключ → `{value, confidence}`. Поле `confidence` — это не часть исходного
ТЗ, а внутренний механизм слияния (см. 1.5): без него новый неуверенный факт мог
бы затирать старый более надёжный.

Факты сохраняются **у сообщения пользователя**, а не у ответа ассистента — самое
свежее пользовательское сообщение с непустым `facts` и есть "текущее" состояние
памяти.

### 1.2. Когда извлечение вообще происходит

Извлечение фактов запускается только если в теле запроса `POST /chats/{id}/messages`
передан флаг `"get_facts": true`. Сервер это не делает автоматически по своей
инициативе — инициатор каждый раз клиент (см. раздел 3, пункт 2).

Перед запуском сервер проверяет (`_validate_sticky_facts_config`, repository.py:562):

* `chat.settings.context_strategy == "sticky_facts"`;
* `chat.settings.context_strategy_limit > 2`.

Если хоть одно условие не выполнено — `400 Bad Request`, извлечение не запускается
вообще (Android-приложение проверяет то же самое на клиенте, чтобы не слать
заведомо ошибочный запрос).

Потоковый эндпоинт `POST /chats/{id}/messages/stream` флаг `get_facts` не
принимает в принципе — извлечение фактов доступно только в блокирующем режиме
(см. раздел 3, пункт 2 — почему).

### 1.3. Поиск "границы" и того, что нужно проанализировать заново

`_load_latest_facts` (repository.py:569) идёт по истории чата **с конца** и
находит последнее сообщение с ролью `user`, у которого `facts` не пусто —
это и есть `existing_facts` + "граница" (само сообщение).

`_dialogue_since` (repository.py:581) берёт из истории **всё, что строго после**
этой границы (или всю историю целиком, если границы ещё не было — самое первое
сообщение в чате). Это и есть тот "новый" диалог, который ещё не учтён в текущем
слепке фактов.

Важный нюанс: если по какой-то причине `get_facts=true` передавался не на
каждом сообщении подряд (например, клиент временно этого не делал), при
следующем вызове с `get_facts=true` в `_dialogue_since` попадут **все**
пропущенные сообщения разом, а не только последнее — механизм устойчив к
пропускам, просто извлечение "догоняет" накопившееся за один вызов.

### 1.4. Изолированный вызов модели для извлечения

`_extract_facts` (repository.py:590) собирает **отдельный, не связанный с
основным диалогом** запрос к модели:

* `system` = `chat.settings.extraction_system_prompt` — по умолчанию заранее
  заданный промпт с точным описанием JSON-контракта (какие два поля на входе —
  `existing_facts` и `new_messages`, какой формат ответа — `{"facts": [...]}`
  с элементами `{"key", "value", "confidence"}`, и правила: не повторять
  неизменившиеся факты, обновлять при противоречии, оценивать confidence и т.д.);
* `user` = один JSON-объект:
  ```json
  {
    "existing_facts": { "...": {"value": "...", "confidence": 0.9} },
    "new_messages": [
      {"role": "assistant", "content": "..."},
      {"role": "user", "content": "<текущее сообщение>"}
    ]
  }
  ```
  (`new_messages` — это `_dialogue_since(...)` плюс текущее отправляемое
  сообщение пользователя, добавленное последним).

Этот вызов **всегда** форсирует `json_mode=True` для запроса к провайдеру,
независимо от того, включён ли `json_mode` в обычных настройках чата
(`dataclasses.replace(chat.settings, json_mode=True)`, repository.py:610) —
это исправление реальной проблемы, из-за которой факты переставали
обновляться после первого сообщения (см. раздел 4).

Ответ модели разбирается терпимым парсером `_parse_json_loose` (repository.py:115),
который по очереди пробует: (1) весь текст как чистый JSON; (2) содержимое
первой markdown-ограды ```` ```json ... ``` ````; (3) подстроку от первой `{`
до последней `}`. Если ни один вариант не разобрался — сервер молча оставляет
`existing_facts` без изменений (ошибку не выбрасывает, чтобы не срывать отправку
основного сообщения из-за сбоя вспомогательного вызова).

### 1.5. Слияние с уже известными фактами

```python
for item in facts_list:                      # repository.py:619-626
    key = item["key"]
    new_confidence = item.get("confidence", 0.0) or 0.0
    current = updated.get(key)
    if current is None or new_confidence >= current.get("confidence", 0.0):
        updated[key] = {"value": item.get("value"), "confidence": new_confidence}
```

Факт полностью заменяется, только если он новый или новая уверенность **не
меньше** старой. Факты никогда не удаляются автоматически — только
дополняются/уточняются. Обновлённый словарь сохраняется в `facts` нового
пользовательского сообщения — он же становится следующей "границей".

### 1.6. Основной запрос ассистенту (это НЕ шаг извлечения!)

Отдельно от извлечения, для собственно ответа модели пользователю собирается
**совсем другой** промпт (`_prepare_send`, repository.py:640, ветка `get_facts=True`):

```
[Известные факты]
{"user_name": {"value": "Алиса", "confidence": 0.95}, ...}

[Последние сообщения]
[user]: ...
[assistant]: ...

[Сообщение пользователя]
<текущий текст>
```

"Последние сообщения" — это **`context_strategy_limit - 1`** последних
сообщений истории (`recent = recent[-(limit - 1):]`, repository.py:656), не
считая текущего отправляемого — то есть в сумме в разговоре участвует ровно
`context_strategy_limit` сообщений (N−1 прошлых + 1 текущее). Обычная полная
история чата в этот вызов **не попадает вовсе** — она полностью заменяется
блоком фактов + этим коротким хвостом. `system_prompt` чата добавляется как
обычно, если задан.

Оба вызова (извлечение + основной ответ) идут внутри одного HTTP-запроса
`POST /chats/{id}/messages`, оба результата сохраняются как два новых сообщения
(`user` с обновлёнными `facts`, `assistant` с обычным ответом) и возвращаются
клиенту одним JSON-телом.

## 2. Цепочка curl-примеров

Ниже — полная последовательность вызовов от создания агента до второго
обновления фактов. Замените `<AGENT_ID>`/`<CHAT_ID>` на id из ответов
предыдущих шагов.

### 2.1. Создать агента

```bash
curl -sS -X POST http://localhost:8000/agent \
  -H "Content-Type: application/json" \
  -d '{"name": "Помощник по миграции БД"}'
```

```json
{
  "id": "ag_3f1c...",
  "name": "Помощник по миграции БД",
  "created_at": 1757600000,
  "updated_at": 1757600000,
  "settings": { "model": "deepseek:deepseek-chat", "...": "остальные поля опущены" }
}
```

### 2.2. Создать чат внутри агента

```bash
curl -sS -X POST http://localhost:8000/agents/<AGENT_ID>/chat \
  -H "Content-Type: application/json" \
  -d '{"title": "Чат 1"}'
```

```json
{ "id": "ch_9a02...", "agent_id": "<AGENT_ID>", "title": "Чат 1", "...": "..." }
```

### 2.3. Включить стратегию Sticky Facts у чата

```bash
curl -sS -X PUT http://localhost:8000/chats/<CHAT_ID>/settings \
  -H "Content-Type: application/json" \
  -d '{"context_strategy": "sticky_facts", "context_strategy_limit": 4}'
```

Без этого шага следующий запрос с `get_facts: true` вернёт `400` (см. 1.2).

### 2.4. Первое сообщение — извлечение "с нуля"

```bash
curl -sS -X POST http://localhost:8000/chats/<CHAT_ID>/messages \
  -H "Content-Type: application/json" \
  -d '{
    "text": "Привет! Меня зовут Алиса, я мигрирую нашу БД с MySQL на PostgreSQL.",
    "get_facts": true
  }'
```

```json
{
  "user_message": {
    "id": 101,
    "role": "user",
    "content": "Привет! Меня зовут Алиса, я мигрирую нашу БД с MySQL на PostgreSQL.",
    "total_tokens": 20,
    "facts": "{\"user_name\": {\"value\": \"Алиса\", \"confidence\": 0.95}, \"goal\": {\"value\": \"миграция БД с MySQL на PostgreSQL\", \"confidence\": 0.9}}"
  },
  "assistant_message": {
    "id": 102,
    "role": "assistant",
    "content": "Приятно познакомиться, Алиса! Расскажите про...",
    "total_tokens": 145,
    "prompt_tokens": 110,
    "completion_tokens": 35
  }
}
```

Здесь `existing_facts` на входе извлечения был `{}` (границы ещё не было),
`new_messages` — только текущее сообщение целиком.

### 2.5. Второе сообщение — извлечение "с учётом истории"

```bash
curl -sS -X POST http://localhost:8000/chats/<CHAT_ID>/messages \
  -H "Content-Type: application/json" \
  -d '{
    "text": "Кстати, сроки поджимают — дедлайн через 2 недели, без даунтайма.",
    "get_facts": true
  }'
```

На этом шаге `_load_latest_facts` находит сообщение `id=101` как границу и
берёт из него `existing_facts` (`user_name`, `goal`), `_dialogue_since` берёт
всё, что после `id=101` — то есть сообщение `id=102` (ответ ассистента).
Извлечение получает на вход:

```json
{
  "existing_facts": {
    "user_name": {"value": "Алиса", "confidence": 0.95},
    "goal": {"value": "миграция БД с MySQL на PostgreSQL", "confidence": 0.9}
  },
  "new_messages": [
    {"role": "assistant", "content": "Приятно познакомиться, Алиса! Расскажите про..."},
    {"role": "user", "content": "Кстати, сроки поджимают — дедлайн через 2 недели, без даунтайма."}
  ]
}
```

Ответ (`user_message.facts` в новом сообщении `id=103`) — старые факты
сохраняются, добавляются новые:

```json
{
  "user_name": {"value": "Алиса", "confidence": 0.95},
  "goal": {"value": "миграция БД с MySQL на PostgreSQL", "confidence": 0.9},
  "deadline": {"value": "через 2 недели, без даунтайма", "confidence": 0.85}
}
```

А в основной запрос ассистенту (не в extraction!) на этом шаге ушло бы
(при `context_strategy_limit=4`, то есть 3 последних сообщения + текущее):

```
[Известные факты]
{"user_name": {...}, "goal": {...}, "deadline": {...}}

[Последние сообщения]
[user]: Привет! Меня зовут Алиса, я мигрирую нашу БД с MySQL на PostgreSQL.
[assistant]: Приятно познакомиться, Алиса! Расскажите про...

[Сообщение пользователя]
Кстати, сроки поджимают — дедлайн через 2 недели, без даунтайма.
```

### 2.6. Проверить итоговую историю и убедиться, что факты накапливаются

```bash
curl -sS http://localhost:8000/chats/<CHAT_ID>/messages
```

Вернёт все сообщения по порядку; поле `facts` растёт только у сообщений
пользователя, отправленных с `get_facts: true`.

## 3. Сравнение с ТЗ

Исходное ТЗ (дословно, три пункта):

> 1. введите отдельный блок "facts" (ключ-значение), который хранит важные
>    данные из диалога (например: цель, ограничения, предпочтения, решения,
>    договорённости)
> 2. обновляйте facts после каждого сообщения пользователя
> 3. в запрос отправляйте: facts + последние N сообщений

**Пункт 1 — реализовано.** Блок `facts` — это словарь ключ → значение
(`{value, confidence}`), хранится персистентно в БД у каждого пользовательского
сообщения. Дополнительное поле `confidence` в ТЗ не упоминалось, но не
противоречит ему — это внутренний механизм, не меняющий внешний контракт
"ключ → важный факт".

**Пункт 2 — реализовано с двумя оговорками.**

* Обновление факта "после каждого сообщения пользователя" на сервере
  происходит только тогда, когда клиент **явно** передаёт `get_facts: true` в
  каждом таком запросе — это не автоматическое, безусловное поведение сервера
  по расписанию или по триггеру "пришло новое сообщение", а флаг, которым
  управляет вызывающая сторона на каждый вызов. Android-приложение это
  учитывает и всегда шлёт `get_facts=true`, пока у чата включена стратегия
  Sticky Facts (`ChatViewModel.sendMessage()`), но это гарантия конкретного
  клиента, а не сервера — сторонний клиент того же API технически может
  отправлять сообщения без этого флага, и тогда факты обновляться не будут,
  сервер об этом никак не предупредит (кроме отсутствия `facts` в ответе).
* Обновление фактов **недоступно вообще** в потоковом режиме — эндпоинт
  `.../messages/stream` не принимает `get_facts` (архитектурное ограничение:
  извлечение фактов требует отдельного изолированного вызова модели, который
  плохо совместим с одновременной потоковой генерацией основного ответа).
  Android-приложение обходит это, принудительно отключая стриминг для чатов
  со стратегией Sticky Facts, но это тоже поведение конкретного клиента.

**Пункт 3 — реализовано, с уточнением "последних N".** Здесь на самом деле
два разных "N":

* в **извлечение** фактов (шаг 1.4) попадает не "последние N", а **весь
  диалог с момента последней границы** — потенциально это может быть больше N
  сообщений, если `get_facts` не вызывался подряд несколько раз, а затем
  вызвался снова (см. 1.3);
* в **основной** запрос ассистенту (шаг 1.6) действительно уходит facts +
  строго `context_strategy_limit - 1` последних сообщений + текущее — то есть
  ровно N сообщений диалога суммарно, как и требует ТЗ, но настройка в
  интерфейсе называется "предел числа сообщений" и указывает именно на эту,
  вторую часть алгоритма, а не на объём данных, уходящих в извлечение фактов.

## 4. Связанная история багов

Ранее (см. предыдущие итерации доработки) факты переставали обновляться уже
после первого сообщения — не потому, что `get_facts` не передавался, а потому,
что вызов извлечения фактов выполнялся с обычными настройками чата, где
`json_mode` обычно выключен: по мере роста истории некоторые модели (особенно
небольшие локальные) начинали отвечать на изолированный запрос извлечения
обычным текстом вместо строгого JSON, разбор падал, и сервер молча оставлял
старые факты без изменений. Исправлено принудительным `json_mode=True` для
этого конкретного вызова (не влияет на `json_mode` основного диалога) плюс
терпимым парсером `_parse_json_loose`, который спасает и обычные, но
markdown-обёрнутые JSON-ответы.
